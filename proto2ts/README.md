# proto2ts

A proto2-subset compiler and shared runtime that turns **actual `.proto` text**
into compilable TypeScript encode/decode modules. No pre-digested field JSON:
the compiler lexes and parses the schema itself, resolves types (including
forward references), and reports every schema problem it finds.

```
src/
  compiler/   lexer.ts  parser.ts  codegen.ts  index.ts   # .proto -> .ts
  runtime/    runtime.ts                                   # shared codec runtime
  cli.ts                                                   # the generator
demo/
  addressbook.proto         # demo schema
  addressbook.pb.ts         # generated by our CLI (npm run gen:demo)
  demo.ts                   # demo consumer program (npm run demo)
test/
  compiler.test.ts  runtime.test.ts  integration.test.ts  cross.test.ts
  gen-fixtures.mjs          # builds binary fixtures with official protoc
  fixtures/                 # generated fixtures (npm run fixtures)
```

## Quick start

```sh
npm install
npm run gen:demo   # compile demo/addressbook.proto with OUR compiler
npm run demo       # run the demo consumer program
npm test           # unit + integration + protoc cross-decode tests
npm run typecheck
```

Using the generator on your own schema:

```sh
npx tsx src/cli.ts my.proto -o my.pb.ts --runtime ../src/runtime/runtime.js
```

The generated module exports, per message `M`: an interface `M`, a descriptor
`M$desc`, and `encodeM(msg): Uint8Array` / `decodeM(buf): M` built on the
shared runtime.

## Supported schema subset

- `syntax = "proto2"` (the line is optional; proto2 is the default), optional
  `package` statement (recorded, not used for naming).
- At most **6 top-level messages**; no nesting, `import`, `enum`, `oneof`,
  `group`, `map`, `reserved`, `option` or `service` — these fail with clear
  errors.
- Fields: `required` / `optional` / `repeated`.
- Types: `int32`, `uint32`, `sint32`, `bool`, `string`, `bytes`, and any
  message declared in the same file. **Forward and self references** resolve
  (types are checked after the whole file is parsed).
- `[packed = true]` on repeated numeric scalar fields (`int32`, `uint32`,
  `sint32`, `bool`); like protoc, the option is rejected anywhere else.
- `//` and `/* */` comments are parsed and carried into the generated
  TypeScript as doc comments (a trailing comment on the same line as a field
  belongs to that field).

Compile-time diagnostics (all problems in a file are reported at once, with
`line:col`): duplicate message names, message names colliding with scalar
types, duplicate field names, duplicate field numbers, illegal field numbers
(`< 1`, `> 536870911`, or in the reserved `19000–19999` range), unknown field
types, misplaced `packed`, and syntax errors.

## Runtime semantics

- **Presence.** `optional` fields map to `field?: T`. A field that never
  appears on the wire decodes to `undefined`; a field present with an explicit
  default value (e.g. `false`, `0`, `""`) decodes to that value and is
  re-encoded. `required` fields are non-optional; `repeated` fields are always
  arrays (`[]` when absent).
- **int32** negatives are sign-extended to 64 bits and encoded as 10-byte
  varints; decoding truncates back to 32 bits. **sint32** uses ZigZag.
  **uint32**/**bool** are plain varints. **string** is UTF-8 (invalid UTF-8 is
  a decode error); **bytes** is copied out of the input buffer.
- **Packed/unpacked.** Repeated packable scalars decode from *both* the packed
  length-delimited form and the unpacked per-element form — mixed in one
  message, in any order — regardless of the declared option. Encoding follows
  the declared option (empty packed arrays write nothing).
- **Merging.** A singular nested message appearing multiple times on the wire
  is merged recursively (singular scalars: last wins; repeated fields:
  concatenate; nested singular messages: recurse; unknown fields: concatenate
  in order). **Required fields are validated only after the entire message
  has been merged**, so a nested message split across chunks — no chunk of
  which is complete on its own — is accepted, while a genuinely missing
  required field still fails, with the full path (`Outer.inners[1].a`).
- **Unknown fields** are kept as raw wire bytes (tag included) on the decoded
  object under a non-enumerable symbol, in their original relative order
  (read them with `rt.getUnknownFields(msg)`). Re-encoding a message — even
  after modifying known fields — appends them unchanged. They stay invisible
  to `JSON.stringify` and enumeration. Byte-for-byte reproduction of the
  original buffer is *not* promised (known fields are re-serialized in field
  order and unknowns move to the end); preservation of the unknown data and
  its relative order is.
- **Wire types** 0 (varint), 1 (64-bit), 2 (length-delimited) and 5 (32-bit)
  only. Wire types 3/4 (groups) fail explicitly. A *known* field number
  arriving with a foreign wire type is treated as an unknown field (and thus
  preserved), matching protobuf behavior.
- **Hard failures** (`rt.DecodeError`): nesting deeper than **8** messages,
  length prefixes beyond the remaining input, truncated or >64-bit varints,
  truncated fixed32/fixed64, field number 0, illegal field numbers. Encoding
  enforces the same depth limit and validates ranges/required fields with
  `rt.EncodeError`.

## Testing and the role of official tooling

`npm test` runs three suites plus integration tests against the generated
demo module. `test/cross.test.ts` verifies interop with the **official
protoc** (from the `grpc-tools` devDependency):

1. fixtures encoded by `protoc --encode` must decode to the expected objects
   with our runtime;
2. our encodings must decode under `protoc --decode` to the same text as
   protoc's own encodings;
3. unknown fields we preserve must be visible to `protoc --decode`.

protoc is used **only** to generate test fixtures (`npm run fixtures`) and to
cross-decode in tests. The production compile and encode/decode paths never
invoke it.
